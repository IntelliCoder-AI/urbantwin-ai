# UrbanTwin AI

**Simulate the City. Solve the Congestion.**

An interactive, Bengaluru-inspired traffic digital twin built for Zeta Innovate 2026. Explore a 3D district, change synthetic traffic conditions, and compare fixed-time and adaptive signals with matched inputs.

> All traffic is synthetic. This is a research demonstration, not a calibrated model of Bengaluru, a forecast of real-world improvements, or a controller for real roads.

## Run locally

Requires Node.js 22.12+ or 24 and npm.

```sh
npm ci
npm run dev
```

Open the URL printed by Vite (normally `http://localhost:5173`). No API keys, paid AI services, database or backend are needed. Fonts and 3D assets are local.

```sh
npm test                 # deterministic engine and recorded evidence tests
npm run build            # TypeScript + production bundle
npm run preview          # serve the production bundle
npm run evaluate         # regenerate 5-seed browser evaluation
```

## What works

- One-junction foundation and four connected junctions with moving vehicles, operational signals, orbit/zoom, intersection selection, congestion overlay, pause/restart and playback speed.
- Normal, rush-hour and incident scenarios; custom seed and demand in live browser mode.
- Synchronized fixed/adaptive counterfactuals, waiting/delay/queue/throughput/stops/fairness metrics, JSON export and five-seed evaluation in a Web Worker.
- SUMO 1.28.0 replay for all three scenarios (seed 42), with a separate five-seed SUMO evaluation.
- Local rules-based traffic assistant, grounded in the displayed metrics, with comparison, fairness and intervention explanations.
- Responsive interface, accessible navigation, local fonts, procedural geometry, and graceful 3D error fallback.

## Two engines, clearly separated

**Live browser model:** a deterministic, simplified microscopic model in TypeScript. Single lanes, straight routes, instantaneous acceleration, 0.5-second steps. It is useful for interaction and hypothesis exploration. It is **not SUMO**.

**Recorded SUMO:** actual Eclipse SUMO simulations generated by Python/TraCI, using a four-junction left-hand network, car-following dynamics and explicit route files. The frontend replays sampled positions and metrics; it does **not** run SUMO in the browser. Recalculate these by running the pipeline below.

Vite + React was selected instead of Next.js because the application needs no server rendering, account system or backend. Static hosting keeps the essential demo free of backend availability and credential dependencies. Three.js/React Three Fiber provide 3D, Recharts provides charts, and the batch worker keeps the interface responsive.

## Reproduce SUMO experiments

Requires Python 3.10+, a platform supported by the Eclipse SUMO wheel, and permission to open localhost sockets for TraCI.

```sh
python -m venv .venv
. .venv/bin/activate
pip install -r simulation/requirements.txt
python -m unittest discover -s simulation -p 'test_*.py'
python simulation/evaluate.py
```

The pipeline generates network XML and route files in `simulation/generated/` (ignored), runs **36 simulations**: three scenarios × (five evaluation seeds + one replay seed) × two controllers, checks collisions/teleports, and writes tracked evidence to `public/data/`. `--quick` regenerates only the three paired replay traces; it does not replace the full evaluation summary.

- Evaluation seeds: 11, 22, 33, 44, 55. Replay seed: 42.
- Arrivals scheduled for 300 seconds, observation horizon 600 seconds, step size 0.5 seconds.
- Demand: normal 0.075 vehicles/s per entry; rush/incident 0.22 for each east/west entry, 0.055 for each north/south entry. Arrivals are independent Bernoulli trials per step.
- Exact route-file SHA-256 recorded per experiment. Both controllers use the same route file and SUMO seed.
- SUMO and browser engines use different random number generators and physical models; compare strategies **within** each engine, never pool engine results.

See [methodology](docs/METHODOLOGY.md) for metric definitions and safeguards and [submission package](docs/SUBMISSION.md) for the competition pitch and demonstration.

## Browser tests

```sh
npm run dev -- --port 5173
# In another terminal:
npm run test:browser
```

Tests cover a desktop and mobile Chromium viewport, play/pause, camera reset, overlay, network and seed changes, the lab, worker experiments, export, assistant, SUMO replay and overflow. By default the test configuration uses `/usr/bin/chromium` if present; otherwise install Playwright Chromium using `npx playwright install chromium`. These are responsive Chromium tests, not evidence of Safari/Firefox or physical mobile-device certification.

## Deploy

The project includes `vercel.json`: framework Vite, build `npm run build`, output `dist`. Deploy the repository to Vercel with Node 24. There are no environment variables or paid integrations to configure. `dist` can also be served by any static host.

## Limitations

The district is inspired by Bengaluru but is not a GIS reconstruction. No calibrated counts, turns, pedestrians, two-wheelers, transit priority or emissions model are included. Incident behavior differs by engine and is documented. Five seeds are a small exploratory sample. Equal mean approach waits do not imply equitable real-world mobility. Green caps prevent phase monopolization, but cannot guarantee bounded vehicle waiting under excess demand. The assistant is an explainable rules engine, not an LLM. There is no persistent multi-user experiment storage. Official competition eligibility, format and deadlines require the Candidate Guide; the November 1 target was provided by the project owner.
